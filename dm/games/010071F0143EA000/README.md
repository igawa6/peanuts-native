# Fire Emblem Warriors: Three Hopes (`010071F0143EA000`)

Update 1.0.2 (v131072) over the base game v0, with its DLC stub (`010071F0143EB001`). SDK 12.3.7. Koei Tecmo's KTGL engine on **NVN**. Modules `main`, `subsdk0` (the movie library, NintendoSDK_movie: WebM movies) and `sdk`. Controller game.

**Status: boots and plays on a Retroid Pocket Nova (Android 13, Adreno 740) with Turnip T30 and R8; the tutorial and the camp are checked there, at about 60 fps.** The profile was written from a survey of the game files and a PC shader split, and the game was packed on a Windows PC (`pack_android.py`). On the Nova it reaches the title and its menus with Turnip and with the system driver, and plays the tutorial and the camp on Turnip (a player's test). Its prewarm seed is left to the maintainer (below). Not checked: the cost of heavy battles, the system driver beyond the title menus, other devices. The run-time keys other than `tbuf_ssbo_copy` are taken from a sibling profile or guessed by rule, none is measured on this game.

## What was found

- **Builds.** `main` `f62a7d41caac7d6d22d5e1384cee3720`, `subsdk0` `bffed55ea46c1b48ddeabcacdfbf81bf` (the movie library), `sdk` `56ec24747ec9e7f19b3efb062483a19d`. `sdk` and `subsdk0` are byte-identical to Fire Emblem Engage's builds ([0100A6301214E000](../0100A6301214E000/README.md)): the `sdk` build has no row of its own in `dm/tools/sdk_patches.py`, so it takes the SDK-wide function rules, as Engage's does. Five instructions are patched, found by matching the function bodies: the two of the AddressRegionManager node area (1 GB to 62 MB) and the three size-class alignments of `AllocateAddressRegion` (regions of 4 MiB and up aligned to 2 MiB). They are written for virtual-address-memory games and this game has none (below), so they are expected to be harmless; keep them in mind if the heap or alias mappings behave oddly.
- **NPDM.** 64-bit, 39-bit address space, main thread priority 44, main stack 1 MB, **system resource size 0** (no virtual address memory: the game sizes its heap with `SetHeapSize`), 47 services.
- **Graphics.** `main` imports `nvnBootstrapLoader` and no other `nvn` symbol, no EGL or Vulkan. No `glslcCompile` import and no GLSLC module: nothing is compiled at run time, so no run-time capture is needed for the shader library.
- **RomFS** (1,770 files, 13.36 GB, the update as one standalone package). The newer RDB, the form of ROMANCE OF THE THREE KINGDOMS 8 REMAKE ([0100C2A01A730000](../0100C2A01A730000/README.md)): `File/CMN/Asset/FDataPackage/Master/root.rdb` and `system.rdb` (`_DRK0000` indexes with a `.rdx` each) over 1,417 `0x<KTID>.fdata` files (`PDRK0000` header, then `IDRK0000` entries; 7.7 GB, the largest 1.6 GB) and 28 `Master/data/*.file` (2.6 GB); 300 loose `.webm` movies (3.0 GB, `File/REGION/WW/Movie/`). `LinkData/` (the older LINKDATA form of Fire Emblem: Three Houses, about 0.07 GB, per-language files under `LANG/`) holds no shaders.
- **Shaders.** `shader_split.py` reads this layout as it is, with no new reader: **63,902 shaders** (pixel 58,808, vertex 4,794, compute 298, geometry 2), 63,767 of them in G2S containers inside the `.fdata` entries and 135 as GLSLC outputs in `main`. The vertex shaders are single-stage programs, paired with a cover of one pixel shader (`shader_pairs.tsv`, 4,794 pairs). `shader_facts.tsv` has the 298 compute answers. The packages are named `<stage>_file.bin` and `<stage>_main.bin` (`shader_groups /File/=file /LinkData/=linkdata`: every shader came from the `/File/` group).
- **DLC.** The 124 KB DLC NSP holds one 312-byte RomFS file (`SUXXORS`): effectively a licence stub. `main` imports `nn::aoc::CountAddOnContent` and `ListAddOnContent`, so the host should report one add-on index.

## Dynamic lights blink between frames

**Current: fixed on Turnip, always on; open on the system driver.** Found on the camp at night (Retroid Pocket Nova, Turnip T30 and R8): the warm glow of lamps, tents and campfires alternated between lit and unlit from one frame to the next while the camera panned; battles use the same lights.

- **Cause.** The clustered light-culling compute shader `afe3b29178c63f21` (23x13x16 groups, local size 64; binding 5, a read-write storage buffer) writes the light lists each frame, and the pixel shaders read them as buffer textures through row-wrap images. The row images came from the CPU's stale bytes, because only texel buffer writes counted as GPU writes. Evidence: skipping that one dispatch (`DM_VK_DISPATCH_SKIP_KEY`) stopped the blinking (0 dropout frames against 20), and no draw-stage shader binds the lists as a storage buffer. `DM_VK_TBUF=0` removes the lights, `DM_VK_WORKER=0` changes nothing.
- **Fix.** The profile key `tbuf_ssbo_copy on` (host switch `DM_VK_TBUF_GW_SSBO`): the lists are copied on the GPU each frame, about 2 copies and 1.67 MB, at most 0.4 ms of GPU time in the camp ([Buffer textures over storage buffer stores read a stale copy](../../../docs/reference/rendering.md#buffer-textures-over-storage-buffer-stores-read-a-stale-copy-android)). The profile key is always on and is not a player setting: the host reads it itself (`vka_draw.c` `TBUF_SSBO_SW`), so no launcher option, recommendation or environment line is involved. `DM_VK_TBUF_GW_SSBO=0` or `1` in the environment (a developer's override: `env.txt`, `env-<title ID>.txt`, Extra environment) wins over the key, and the host logs the value that applies and why at start: `tbuf ssbo: GPU copy of buffer textures over storage buffer stores on (profile tbuf_ssbo_copy on; DM_VK_TBUF_GW_SSBO unset)`. One-frame dropouts of a camp pan: T30 14 to 0, R8 4 to 0. A player confirmed that the camp lights no longer blink (T30).
- **System driver.** Not fixed: the copy needs placed guest memory, which Qualcomm's driver does not give, so the switch declines (`tbuf ssbo ... row image stays`) and the blinking stays. Known issue; use a Turnip driver. Inferred from the code, not run on a device.
- **Open.** The cost in heavy battles (1,000-1,700 draws) is not measured. The `[RED] vk: texture ID ... beyond the table` line once per run after the camp loads is a separate lead, not tied to this.

## Prewarm seed

The profile has no `vk_prewarm.bin`: the maintainer builds the seed, and the key list of this fork's runs is available on request. That list is **695 pipeline keys** (657 vertex, 38 compute; key size 992, key layout `3710792d`, 294,976 bytes), the `vk_pipelines.keys` list of the Nova's own runs, which `dm/tools/vk_prewarm.py seed 010071F0143EA000 <keys>` writes into the profile. Recorded 2026-11-24 on a Retroid Pocket Nova (Turnip T30 for most runs and Turnip R8 for some; the static-input keys below presumably come from system-driver runs), from the boot, the title and its menus, the tutorial, the camp at night, and one player's route of about 21 minutes (76,500 frames, scenes of up to 2,150 draws a frame, two movies). 503 of the vertex keys use vertex input dynamic state (Turnip) and 154 are of the static vertex input path (system driver): a Turnip start drops the 154 at once (`dropped ... another device's keys` in the prewarm line) and keeps them in the list. Recorded by earlier host builds of this fork (the key layout, `vka_gkey`, is unchanged since: the list's layout fingerprint equals the current host's `vka_pw_layout`). Before the seed, a start prepared only the keys of the earlier runs of the device itself (656 to 658 keys, 0.2 s with a warm cache), and a fresh install had none. The effect of the seed on a start is not measured yet. Make it again from runs of the new host after any change to `vka_gkey` (`dm/gfx/vk_android/vka_gkey.h`).

## Open

- **Run on one device only.** The Nova is the only device it has run on. Everything above that is not a file fact or a measured fact is a guess or a sibling's value: `mem_used` margin, `tex_flush_upload`, `vconv_range`, `pad_layout`, `op_mode`.
- Heap check: the first Android logs on the Nova show no `SetHeapSize` failure (heap 3.14 GB), so the default `mem_used` holds there (see `mem_used` above); other devices are not checked.
- Which of `main`'s 450 imports have no host hook (`swkbd`, `nfp` amiibo, `ngc` profanity filter, `account`, `aoc`, `HardwareOpus` decoders) has not been checked against the host's hook table.
- The SDK-wide `sdk` rules (node area cut and 2 MiB region alignment) apply to this build (above). Checked on a Retroid Pocket Nova (Android 13, Adreno 740, Turnip driver) with these rules in place: the game starts, loads a save into the Chapter 3 camp and runs it at about 60 fps with the usual 3.14 GB heap, with no heap-size failure and no address-region call in the log. No battle was run in this check. No effect is expected, because without virtual address memory the game sets a heap with `SetMemoryHeapSize` and `main` imports no address-region call; every Nova log has the 3.14 GB heap line and no address-region line (the host logs regions of 256 MB and up). Smaller regions are not logged.
- Frame rate: the Switch game's own pacing is untouched. The `fps_limit`, `fps_modes` and `fps_default` rows only set the Frame rate slider's steps and its start at 60 fps; 20 and 45 fps are not device-tested.
