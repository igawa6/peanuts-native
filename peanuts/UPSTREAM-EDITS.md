### Round 8, after the first device run (2026-11-15): queued region writes and forced image drops

Breath of the Wild at 1.5x aborted after 131 s in `img_destroy` (a second free). The cache gives an image up whatever its reference count in two places
(eviction, `vka_tex_prune_locked` / `img_evict_locked`, and `vka_tex_drop_pool`), and a queued region write (`mtl_tex_write_region`: WriteTexels) holds its
image by pointer with a reference only. An image the game writes but has not drawn for two frames can be evicted and freed at once with writes still queued;
the next prepare then copies into, and releases, whatever has taken the freed `vka_img`'s memory. With the resolution scale that can be the old image of an
in-place swap (it was made right after a prune, with a count of 1), which the stray release destroys once more than its own callback. Without the scale the
same stray release lands on a new image of the cache. This is the cause as far as reading the code and a model of it go
(`dm/host/tests/t_android_imglife.c`, `make android-imglife`; `build/t_android_imglife old` shows the fault); it has not been confirmed on the device.

Texture readback. A module asks for one texture's level 0 as R8 or as four bytes a pixel, by the address of its storage or as the newest of a size, optionally only
colour targets, only sRGB or linear ones, only ones drawn into in two frames. The request is only queued; the present thread picks the image under the texture cache's
lock with the runtime's own rule, holds it, records one `vkCmdCopyImageToBuffer` into the present's command buffer (the method of `DM_VK_IMG_DUMP`'s diagnostic) and
hands the bytes to a worker thread when the present has next waited for that submission's fence (three presents later; no fence is queried, since a status query
blocks on the drivers `vka_dev.c` probes for). The present's command buffer is queued ahead of the batch still being recorded, so each image carries the fence of the
batch that last wrote it: a copy reports the newest generation whose batch is on the queue, and an image made or first written in a batch not yet queued waits for
the next present. A request no present takes within two seconds is answered as failed by the next request, so a paused game never leaves the two slots taken.
Formats are the emulator's: plain 8-bit R8, RGBA8 and BGRA8, linear or sRGB, the stored bytes; nothing compressed, float, packed or multisampled. The limits are
the runtime's (2048 a side, 16 MiB, two requests a second, two at once), so at most 32 MiB a second is copied. With no request queued the present pays one relaxed
load and a branch; a GPU write's note, a new image's first use and a colour target's site pay one each, false until a companion's first request. A rescaled image
(`DM_RES_SCALE`) is not read. A request's address is the texture's storage address in the game's memory: this host has no GPU address space.

of `DM_AOC_DIR` (a folder, a `.nup` or a dump; when that index cannot be read, nothing). The battery is what the app pushes through `Bridge.battery`, else the
kernel's power supply files. `@perf.fps` counts the replay's frames; `@perf.frametime_ms` is the GPU's busy time a frame (the emulator's is a frame's time without
its waits). A manifest's patches are written with the game's threads stopped and no thread inside them, only where main holds the file's own instructions and what
it held before the package's load plan was installed; a patch that cannot be written just now is tried again on later ticks; the pages keep their protection.

## Android presentation deadline forwarding

The active game Activity forwards `Display.getPresentationDeadlineNanos()` once during `hostSetup`, then through the existing 500 ms `fpsTick` while active. A missing display sends zero. The JNI bridge preserves positive nanosecond values as 64-bit unsigned values, normalizes nonpositive values to zero and safely ignores a host without the new weak interface. The renderer uses this platform queue-lead requirement when selecting its target presentation grid; half a refresh alone does not describe the compositor's deadline. See the [Android API contract](https://developer.android.com/reference/android/view/Display#getPresentationDeadlineNanos()).

There is no additional timer or persisted preference; the first tick after resuming a paused loop can take up to two seconds. Deadline-aware physical 120 Hz testing still showed uneven presentation despite sufficient reported queue lead. Forwarding the deadline corrects the source's platform contract but does not establish a cure for that platform behavior.

| Files | Marked hook | Purpose |
|---|---|---|
| `GameActivity.java` | `presentationDeadlineUpdate`, `hostSetup`, active `fpsTick` | Forward the current display's required queue lead |
| `Native.java`, `nxlaunch.c` | `presentationDeadlineSet`, weak forwarder | Preserve nanoseconds and handle missing hosts |
| `vk_android.h`, `vka_present.c` | `nxhost_presentation_deadline_set` | Expose and consume the platform's compositor deadline |

`peanuts/tests/test_presentation_deadline.py` compiles the production Activity forwarding helper against JVM stubs and the production JNI bridge against the exported C header. It checks deadline changes, missing displays, 64-bit values, signed-input normalization and unavailable weak host symbols.

### Stable 30 display-mode platform mitigation

For the owner's Stable 30 preference, the game Activity requests a same-resolution mode within 0.5 Hz of 60 Hz only when the fourth field of the running native cap status is 30 and requested native FG state is explicitly off. The third status field is the configured game rate, not an observed frame count; zero means unavailable state. Pending restart preferences never drive this request. Every other cap, unavailable state, FG enablement, pause/background transition and destruction releases it. No global setting is changed.

Final combined physical 60 Hz menu/outdoor/movement windows measured 630/630 uniform two-refresh intervals (378 while walking or moving the camera) while nominal 120 Hz retained 12–18 short/long pairs per 126 intervals despite the platform deadline lead. The remaining high-refresh compositor/HWC cause is open. This is an explicit platform mitigation for stable 30 fps, not a demonstrated root-cause cure; mode selection remains an asynchronous platform request.

### Round 51, the steady clock runs through sleep and restarts (2026-11-21, GitHub issue #329)

Tomodachi Life: Living the Dream warned at most starts that the system time had changed, and its fountain, market and new foods stopped for days. The host's steady clock was the monotonic clock under one fixed source ID; on Android it stops in deep sleep and starts again at 0 at every boot, so the user clock context's offset grew by every hour the phone slept and `CalculateStandardUserSystemClockDifferenceByUser` reported the sleep as the user setting the clock; read from the two clocks one after the other, it could also come out a second off between two starts. The game then shifted every timestamp in its save by that change, and the time slept never counted. One reading of the host's real-time clock now gives the steady clock (in seconds, the new source ID `dmhost-steady-02`) and the user clock (the same reading plus `DM_TIME` / `DM_TIME_OFFSET`'s offset), as an RTC-based steady clock runs; the first eight comparisons of two steady clocks or a user change are logged. Measurements are in the [game note](../dm/games/010051F0207B2000/README.md#time-and-the-clock-check).

### Round 54, the steady clock anchored: one real-time reading a run, then the boot-time clock (2026-11-22, the review of PR #336, PR #365)

Round 51 (PR #336, the steady clock runs through sleep and restarts) made the steady clock the host's `CLOCK_REALTIME`. That clock steps when Android corrects the phone's clock from the network or the carrier, backwards too, and a span between two steady time points of one run could then come out negative, which a Switch never gives. As igawa6 asked in the review: the real-time clock is read once a run, at the first call, and advanced by `CLOCK_BOOTTIME`, which only goes forward and counts deep sleep (Apple: `CLOCK_MONOTONIC`, which counts sleep there).
